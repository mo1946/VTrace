# VTrace 会议复盘

从会议原始证据整理决策和后续行动，明确区分讨论、提议、正式决定与未解决问题。按用户要求控制复盘范围，不替用户分配任务或发送通知。

## 连接与视频选择

- 使用 VTrace MCP 的实际工具。当前连接标识为 `seeit-ai`，`seeit://` 资源 URI 和 `SEEIT_*` 配置继续兼容；MCP 请求走 Python API，不自动切到前端的 Java 路由。
- 已知 `media_id` 时直接读取；否则用 `list_media` 结合用户描述定位，只有目标仍有歧义时询问。用 `get_video_metadata` 确认证据数量与来源。
- BV 输入可通过 `preview_bilibili_video`、`import_bilibili_video` 和 `get_bilibili_import_status` 接入，完成后使用 `mediaId`；本地录像需先由网站上传。导入完成仅代表视频入库，不代表会议分析已完成。
- 保持用户身份与资源归属边界。401/404 不能视为视频没有内容，不输出令牌或绕过 MCP 查库。

## 证据工作流

1. 全会复盘先通过 `get_video_timeline` 分时间段浏览，再围绕议题检索。该工具单次最多 200 条，返回数达到上限时继续缩小时间窗口并去重；明确尚未覆盖的范围。
2. 使用 `search_video_evidence` 分别检索决策、行动和问题，例如“决定、通过、否决”“负责、交付、截止”“阻塞、依赖、分歧”。优先 ASR/OCR，忽略 `SYSTEM` 占位证据。检查返回的覆盖与充分性信息（若有），避免只摘取同意某一方案的片段。
3. 对候选事项调用 `get_evidence_window`，检查后续是否撤回、修订或被否决。保留需要合并的重复事项及其前后变化，会议后段不自动优先于明确的决策依据。
4. 负责人只能来自明确的指派或承诺。当前 ASR/OCR 不保证说话人身份识别，不根据“我来做”、声音印象或职位自行填姓名。相对期限缺少会议日期时保留“下周三”等原话，不换算为当前日期。
5. 使用 `verify_video_citations(media_id, citations)` 批量核对引用；每项使用原始 `timestampMs`、`source`、`content`。工具通过后仍判断证据是否支持事项的完整含义，特别是负责人、期限和决定状态。

## 输出

遵守用户格式；默认提供会议概览、已确认决策、行动项表、风险与未决问题。行动项表可包含：事项、负责人、截止时间、会上约定的状态、原文依据和时间戳。

- 缺失负责人、期限或状态时写“未明确”，不要为了表格完整而推测。
- “建议下一步”与“会议已分配事项”分开；后者必须有证据。不要把会上承诺完成等同于实际已经交付。
- 每项决策和行动保留 `[MM:SS]` 与 ASR/OCR 来源。识别错误、时间轴截断和无法确认的说话人应明确标出。
- 跨片段综合可以归纳主题，但涉及推断时标明“视频未明确说明”；没有支持时保留未决，不强行给结论。

## 平台报告与追问

需要准备证据或用户要求保存复盘时，调用 `start_video_analysis(media_id, goal)`，例如“复盘会议议题、正式决策、行动项、明确负责人和期限，列出风险与分歧，并逐项引用时间戳”。

用 `get_analysis_status(task_id)` 查询，间隔不少于 3 秒。重复任务响应有 `taskId` 时恢复该任务，无 ID 时用 `get_analysis_report(media_id, goal)` 检查对应任务，不盲目重发。排队、执行中、重试中应如实展示；失败时返回错误，不自动无限重建。完成后读取同目标报告，`answerable=false` 不等于已有可靠决策。需要交还控制权时返回任务 ID 和当前状态。

追问可用 `ask_video`，恢复历史可用 `get_agent_memory`；会话历史不能替代会议原话证据。
